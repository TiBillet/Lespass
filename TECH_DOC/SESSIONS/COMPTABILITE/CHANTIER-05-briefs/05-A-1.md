## RÈGLE ABSOLUE — À LIRE EN PREMIER
AUCUN commit, AUCUN `git add`, AUCUNE commande git destructive (`checkout --`,
`restore`, `stash`, `reset`, `clean`). Lecture seule autorisée (`git status`,

deux pytest en parallèle (`docker exec lespass_django pgrep -af pytest` avant de lancer).

byobu).

## RÈGLE DE LISIBILITÉ — À LIRE EN DEUXIÈME
Lespass est un **commun numérique** : le code doit être lisible et compris par un humain
non expert. **Avant d'écrire la moindre ligne** (code ou test) :
1. charge le skill **`djc`** (outil Skill) ;
2. lis **`GUIDELINES.md`** (racine), au moins « FALC », « Architecture »,
   « Anti-patterns », « Tests » ;
3. charge le skill **`tibillet-test`** et lis `tests/PIEGES.md`.

L'essentiel : noms verbeux, explicite plutôt qu'implicite, boucles `for` simples, pas de
magie (pas de métaclasse, pas de décorateur qui cache la logique) ; docstrings avec
LOCALISATION et FLUX ; commentaires **FR puis EN**, FALC, **au présent**, adressés au
prochain lecteur (jamais le récit de ta session) ; `_()` en **français**. Un code qui
passe les tests mais ne respecte pas ces règles n'est pas terminé.

## Étapes
1. Écrire les tests. **Ne pas écrire de code de production.** Les lancer
   (`make test ARGS="tests/pytest/test_montants_article.py tests/pytest/test_vente_modeles.py"`),
   coller la sortie d'échec (import absent → `ImportError` : le noter tel quel). Puis
   **STOP** : l'orchestrateur relance lui-même pour prouver le rouge.
2. (après feu vert) Modèles, migrations, formule, marqueur, T1. Appliquer les
   migrations. Relancer les tests de A-1, puis les 22 tests de caractérisation, puis
   `manage.py check` et `makemigrations --check --dry-run`.
3. Ne pas jouer les mutations : pour chaque mutation de la fiche §7 qui concerne A-1
   (`ROUND_HALF_UP` → `ROUND_HALF_EVEN` ; TVA calculée à part ; `save()` réapplique la
   TVA sur un 0 ; défaut seulement si `vat is None` ; coût sur `quantite` ; retirer une
   `CheckConstraint`), donner fichier:ligne, texte avant / après, test attendu en échec.
   Pour une `CheckConstraint`, dire si la mutation exige une migration (sinon, muter en
   base n'est pas possible : proposer la mutation la plus simple qui reste vraie).
4. CHANGELOG (migration : **oui**, noms des deux migrations et commande ; chaînes i18n
   ajoutées : natures, statuts, sources d'offert, libellés de champs).
