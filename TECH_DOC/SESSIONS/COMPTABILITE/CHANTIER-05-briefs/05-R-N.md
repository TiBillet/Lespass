## Comportement attendu (fiche §18)
- Options : `--executer` (sinon à blanc), `--liste <fichier>` (un domaine par ligne ;
  **obligatoire** avec `--executer`), `--jours-minimum N` (défaut 60), `--rapport <chemin.csv>`,
  `--traces-externes <chemin.csv>`, `--sans-mail`.
- Sortie : deux listes — **à supprimer / supprimés** (domaine principal, date de création, raison
  « aucune activité ») et **gardés** (domaine principal, date de création, toutes les raisons, une
  raison = un critère du tableau §18 nommé en français). Puis un résumé chiffré. Le lieu est
  **toujours** désigné par son domaine principal ; un lieu sans domaine principal (pool) n'apparaît
  pas (critère 1).
- Avec `--executer` : un lieu supprimé = dans la liste ET inactif maintenant ; un lieu de la liste
  redevenu actif est gardé et signalé (« dans la liste, mais actif maintenant : <raisons> ») ; un
  domaine de la liste inconnu est signalé.
- Une transaction par lieu, dans cet ordre : lire ses traces externes (Stripe Connect, place
  Fedow) ; `DROP SCHEMA … CASCADE` ; `client_source` → NULL ; lignes M2M du lieu retirées ;
  `AuthBillet_wallet.origin` → NULL ; `MetaBillet_waitingconfiguration` du lieu **supprimée** ;
  `seo_seocache` et `onboard_onboardinvitation` du lieu supprimés ; domaines ; `Client` ;
  **puis contrôle par le catalogue** : plus aucune ligne, dans aucun schéma, ne pointe vers le
  lieu, sinon exception (la transaction est annulée et le schéma revient). Un échec sur un lieu
  n'arrête pas les autres : il est rapporté.
- SQL brut seulement (aucun modèle Django lu ni écrit, ni `Client`, ni `Configuration`) : la
  commande doit marcher **avant** les migrations de la branche (base de `main`) et **après**.
  Critère 6 : les défauts du modèle `Configuration` se lisent dans `_meta` (sans requête) ; une
  colonne absente de la base est sautée.
- Critère 5 : la liste des tables « remplies seules » est **explicite** dans le code, commentée
  table par table (d'où vient la ligne : onboarding, migration, singleton créé à la lecture).
  Établis-la sur un lieu neuf de test **et** pour la base de `main` (ex. `comptabilite_comptecomptable`
  semé par `main:comptabilite/migrations/0002`), dis comment dans le rapport.
- **Mail aux administrateurs** (fiche §18, texte à reprendre tel quel, msgids en français) : adresses
  des admins (`client_admin`) lues **avant** le `DROP` ; envoi par une tâche Celery (`.delay()`)
  dans `transaction.on_commit` (rien si la transaction est annulée) ; **un mail par administrateur**
  qui liste ses lieux supprimés ; réutilise le mécanisme d'envoi existant du projet (cherche-le :
  `CeleryMailerClass`, gabarits de mail existants) ; `--sans-mail` n'envoie rien. Aucun mail à blanc.
- Aucun autre appel réseau.
