## Pourquoi
À la session suivante (C-1), chaque tirage facturé par `controlvanne/billing.py`
`facturer_tirage` écrira une **vente scellée** (numérotée, chaînée) avec ses règlements.
Or plusieurs fichiers de tests controlvanne passent par la vraie route `pour_end` sur la
base partagée `lespass` **sans** `django_db` :
- ils laissent déjà leurs lignes en base de dev (54 lignes `TIREUSE`, toutes de tests,
  comptées le 2026-09-30) ;
- après C-1, leurs nettoyages manuels tomberaient en `ProtectedError` : `Vente.point_de_vente`,
  `Reglement.carte`, `Reglement.wallet` sont en `PROTECT` (ex. `test_controlvanne_billing.py`
  ~l.508-513 supprime carte et wallet ; fixture ~l.150-159 supprime le point de vente).

Même piège que la caisse en B-3b-1 (`CHANTIER-05-SUIVI.md` §8, 2026-09-29) : tout test qui
facture par une route doit être `django_db` (tronc §8.5).

   `tests/pytest/test_pos_vider_carte.py`). Le test vérifie **exactement la même chose**
   qu'avant : mêmes scénarios, mêmes assertions.
3. **Retirer les nettoyages devenus inutiles** : dans le corps d'un test `django_db`, un
   objet créé **dans le test** disparaît au rollback ; son `delete()` manuel est à retirer
   (sinon `ProtectedError` après C-1). Les objets créés par une fixture de **session ou de
   module** (hors transaction du test) gardent leur nettoyage de fixture.

## Points d'arrêt (ne pas contourner, rapporter)
- Un test qui dépend d'un **solde laissé par un test précédent** (portefeuille d'une
  fixture de session débité d'un test à l'autre) : le rollback remet le solde. Ne rien
  bricoler : rapporte le test et ce qu'il attend.
- Un test qui attend un effet d'un `transaction.on_commit` (diffusion WebSocket de l'état
  de la tireuse ou du stock) : sous `django_db`, rien n'est commité. Rapporte-le, avec la
  piste `django_capture_on_commit_callbacks(execute=True)`, sans l'appliquer d'office si
  cela change ce que le test vérifie.
- Un test qui ne peut pas passer en `django_db` sans changer ce qu'il vérifie : STOP.
