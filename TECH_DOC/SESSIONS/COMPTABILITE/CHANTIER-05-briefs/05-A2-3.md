## RÈGLE DE LISIBILITÉ — À LIRE EN DEUXIÈME
Lespass est un **commun numérique** : le code doit être lisible et compris par un humain
non expert. **Avant d'écrire la moindre ligne** :
1. charge le skill **`djc`** (outil Skill) — en particulier « FALC Commenting Method »,
   « Le commentaire s'adresse au PROCHAIN LECTEUR » et « Tests / Règles d'or » ;
2. lis **`GUIDELINES.md`** (racine du projet), au moins « FALC », « Tests »,
   « Anti-patterns » ;
3. charge le skill **`tibillet-test`** et lis `tests/PIEGES.md` (au moins 9.x, 13.x).

Pour un test, cela veut dire : noms de tests et de variables verbeux ; un test = un
parcours ; docstring FR puis EN qui dit **ce que le test fige**, au présent ; boucles
`for` simples, pas de compréhension imbriquée ; dictionnaire attendu écrit **en clair**
dans le test (pas calculé) ; aucun `pytest.skip`, aucun `if ... count() > 0`, aucune
assertion toujours vraie. Un test vert mais illisible n'est pas terminé.

## Particularité de A′ : pas de rouge
Un test de caractérisation fige le comportement **actuel** : il est **vert** sur le code
actuel. Sa force est prouvée par les **mutations** que l'orchestrateur joue ensuite.
**Tu ne modifies aucun code de production.** Si un comportement te semble faux : tu le
figes tel quel, tu écris dans le docstring « comportement actuel figé (voir T… ) » et
tu le signales au rapport. Les tests qui changeront en D / G / H (fiche §4) figent eux
aussi le comportement **actuel** ; leur docstring le dit (« change en D, décision
D30 », etc.).

## Ce que la spec ne dit pas
Si l'annexe est muette, ambiguë ou fausse face au code (un statut attendu n'est pas
celui du code, une tâche n'existe pas, un parcours n'est pas atteignable avec
l'outillage) : **ne pas inventer**. Écrire le constat (fichier:ligne, ce que dit
l'annexe, ce que fait le code). S'il s'agit d'un **statut ou d'une tâche différents de
l'annexe**, fige le **code** (c'est la règle de la caractérisation) et signale l'écart ;
si le parcours est **impossible** à écrire, STOP.
