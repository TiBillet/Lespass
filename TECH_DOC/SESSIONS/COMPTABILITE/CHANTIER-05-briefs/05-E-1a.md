1. **Les données du plan par défaut** dans un module de **données seules** (par exemple
   `laboutik/plan_comptable_par_defaut.py`) : la liste des comptes de la fiche §3.4

   migration et le chargeur le lisent tous les deux.
2. **Une seule fonction de chargement**, idempotente, qui **ajoute ce qui manque** sans
   rien effacer ni renuméroter (`get_or_create` par `numero_de_compte`, correspondances
   créées seulement si absentes). Elle sert : la commande `charger_plan_comptable`, le
   bouton de l'admin, la migration (sa version `apps.get_model`) et le **filet**
   `s_assurer_que_le_plan_existe()` (charge le plan si le lieu n'a **aucun** compte ;
   `atomic`, `IntegrityError` attrapée : deux appels simultanés ne cassent rien). Le
   filet n'est **appelé** par personne en E-1a (E-2 et F le brancheront) : seulement
   testé.
3. **Les profils `bar_resto` et `association` disparaissent** (plan unique, mainteneur) :
   la commande perd `--jeu` (et `--reset` si c'est son seul usage) ; le bouton de l'admin
   (`laboutik/views.py` l.4176-4210) charge le plan par défaut **sans rien effacer**
   (`reset = nb_existants > 0` l.4203 supprimé) ; son bandeau
   (`Administration/templates/admin/comptable/changelist_before.html` l.16) dit vrai.
4. **Unicité de `numero_de_compte`**, trois migrations dans `laboutik` :
   (a) `RunPython` de **dédoublonnage** par numéro (garde le plus ancien, repointe
   `CategorieProduct.compte_comptable` et `MappingMoyenDePaiement.compte_de_tresorerie`,
   supprime les autres ; ne fait rien dans `public`) ; (b) la contrainte d'unicité ;
   (c) `RunPython` qui **charge le plan par défaut** dans tout lieu qui n'a aucun compte
   (elle couvre aussi les lieux créés plus tard : `auto_create_schema` rejoue les
   migrations). Les `RunPython` ont une fonction inverse qui ne fait rien.
